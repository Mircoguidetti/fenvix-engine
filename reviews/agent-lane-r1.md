## Verdict in one paragraph

The lane's core safety holds in my reruns and in every attack I made on the write path: no acknowledged write lost, no fenced primary confirming, no gap or duplicate in the WAL numbers, mixed transactions atomic. But I found one lane bug that loses data and brings deleted data back (R3, the spare's follower), and the Q8d read fix, which the lane depends on, swaps one guarantee-3 hole for another: reads now see writes that are not durable yet, and lose them in a crash (R2 with the lane, R5 without it). The warm spare does not read the log's records at a live takeover (R4): every default-path write acknowledged in the last upload interval is missing on the spare. That one is old (on integration too) and the owner disclosed it, but the contract's point 3 ("the spare after takeover serves every confirmed write") passed only because test t3 sleeps 7 s, one upload interval, before the kill.

## The failing tests (each fails on 8fbdd8d)

**R3 `r3_spare_cache_after_drop.py` (the lane; guarantees 1 and 6).** The spare's follower (`agentlane.rs`, `FollowStore`) keeps every WAL object it fetched in memory, by path, and answers slatedb's reads of that path from memory. `dropDatabase` deletes every object, and the recreated database writes its WAL again from number 1 at the same paths (`tenants/{db}/wal/NNN.sst`). At takeover the spare replayed the dropped database's objects instead of the new ones. Result: 40 dropped documents back, 5 of 5 acknowledged new documents missing (FAIL). Control `--control` (same spare, no follower): 0 back, 0 missing (PASS), so the follower is the cause. Why it matters: an acknowledged write is lost and erased data comes back (the "erase a user" problem E of NOW.md), silently, on the failover path. Any reuse of a path does the same (drop/recreate, an erase, a restore). Fix direction: key the kept objects by the object's identity (ETag/version or the manifest's writer epoch), drop them on a NotFound or a drop, and never answer a read from memory without checking it is the stored object (a HEAD costs a GET price; or keep the follower's view only for numbers above the manifest's `replay_after_wal_id` of the same incarnation).

**R2 `r2_visible_before_durable.py` (the lane plus the Q8d read fix; "a write visible before it is durable").** An agent-lane insert waiting for its PUT (window 4 s in the test so the wait is easy to land in; at 100 ms the exposure is the window plus one PUT) is returned by a read with readConcern "majority" and announced by a change stream; kill -9 before the PUT loses it. 3 rounds: 3 majority reads of the unacknowledged write, 3 change-stream events, 3 seen-then-lost (FAIL). MongoDB never returns rolled-back data to a majority read and change streams report only majority-committed changes (DECLARED, MongoDB manual: read concern "majority"; change streams). Control `--control` (lane without the log, so reads stay on durable data): 0 seen-then-lost (PASS). The owner disclosed "majority answered like local"; I count it because the coordinator's list names this case and the lane makes the window 100-300 ms wide (ESTIMATED from t5), not microseconds. An agent framework that reads its checkpoint back from another worker can act on a step that then disappears.

**R5 `r5_log_visible_before_durable.py` (the Q8d fix alone, lane not used).** Replicated log on, the 3 copies frozen (SIGSTOP) so a default-path insert cannot be confirmed; a majority read returns it; kill -9. 3 rounds: 3 majority reads of the unconfirmed write, 2 lost after the restart (FAIL on 8fbdd8d). On integration d6ce3d4: 0 reads of it (PASS). So the fix in `dbs.rs` (`durable_reads` false whenever the log is on) creates dirty reads on the default path too. Why: with the log on, "durable" means "in the log", but the fix reads the writer's memtable, which holds writes staged before the log confirmed them (and writes the log refused stay in the memtable).

**R4 `r4_spare_takeover_log_records.py` (Q8d log path, lane or not; guarantees 1 and 3 on the spare).** Same set-up as t3 (3 log copies, two engines on one store, lease 4 s, upload every 30 s); the primary writes 200 default-path documents with w:majority and is killed at once. The spare, after the takeover, serves 0 of the 200 (FAIL on 8fbdd8d; FAIL on integration d6ce3d4 too: old). The owner's open item says it ("a live takeover does not read the log's records"); t3 hides it (`time.sleep(7)` before the kill, commented "one upload of the log puts the default-path writes in object storage"). I count it because the coordinator asked to check the warm spare for the same hole, and because the contract's point 3 was reported PASS on a test that cannot see it. Not the lane's fault; it blocks the warm spare with the log, lane or not.

## The Q8d fix (the coordinator's first question)

- Reproduced on integration d6ce3d4 (R1 `r1_log_read_your_writes.py`, local log on, lane off, 50 rounds): point read by _id 50 misses of 50, count 50/50, aggregate $match 50/50, the value after an update 50/50 stale (the OLD value came back, worse than a miss), a transaction's writes read after its commit 50/50; reads through a secondary index, range reads, the absence after a delete and a read inside a transaction 0 misses. On 8fbdd8d: 0 misses on all nine (PASS). So the bug is real and the fix removes it for every read path on the primary (get, scan, meta reads all go through `durable_reads`; `get_many` already read the latest state).
- Not complete: the warm spare (R4) and dirty reads (R5). A correct fix reads "everything the log or object storage has confirmed, nothing else": for example serve the latest state only up to the highest batch whose log record (or WAL object) is confirmed, or hold a read that touches a key with an unconfirmed staged write until it is confirmed (MongoDB-like "majority" behaviour; "local" may keep the fast path if the product wants it, said plainly).
- Other read paths: transactions (snapshot reads inside a transaction, commit then read): fine on 8fbdd8d (R1). The first course is not on `integration` (no code to check). Range and index reads: fine (R1). The warm spare: R4.
- NOTE (code reading, not turned into a test): `src/lifecycle.rs` `Tenant::close`, the fallback "final flush did not finish ... closing without it": its comment says "everything acknowledged is in durable WAL objects", which is false with the log on (the WAL is flushed only every 30-60 s; slatedb 0.17 `CloseOptions { flush_type: None }` does no flush, "writes that are not durable may be lost", DECLARED in its source). The database is then reopened and served without those writes until a restart replays the log, and a new writer epoch makes that replay a conflict. Needs an L0 stall to trigger; not lane-specific.

## The lane's safety: what I re-ran and attacked (all on the build of 8fbdd8d)

- Owner's t1 durability, 30 kill -9 (10 random, 10 inside a WAL PUT, 10 between PUT and acknowledgement, every second restart with the local disk wiped): 4,812 acknowledged writes (3,536 on the lane), 1,339 transactions, 1,228 hot versions; lost 0, torn or stale 0 (PASS).
- Owner's t2 one writer, 12 trials (6 frozen primary on MinIO, 6 two live primaries): 1,108 acknowledged, lost 0, fenced acknowledgements 0, A acknowledging after its wake 0, WAL gaps 0, duplicates 0 (PASS). The check is strict: it counts every acknowledgement from the frozen primary after its wake, and there were none in the owner's 50 trials either.
- Owner's t3 read your writes, reduced (10,000 lane writes, 10,000 lane transactions, 2,000 default-path writes, 64 threads): 0 misses; the spare served 32,000 of 32,000 after the takeover, first read 5.21 s after the kill (PASS; but see R4 for what its 7 s sleep hides).
- Older log record over a newer lane write (bug 1 of the owner): by reading, the fix (`Record::orig`, compare and mark with the staged number) is sound; the argument it relies on also holds: a lane batch is durable only when its WAL object is, and that object holds every batch staged before it with its log marker, so the marker covers every earlier log record. The owner's hot-document check in t1 saw 0 stale in my 30 kills.
- Mixed transactions: go on the log as one record (`agent_lane_batch` refuses any batch with a non-lane collection or a catalog key). Atomic in t1 (0 torn). Not re-run against mongod (t4) for time; the owner's log shows 0 differences.
- Catalog or index keys on the lane: by reading `classify`, only `doc/ idx/ idc/ nat/` and the per-collection counters go on the lane; index definitions, options, the collection list and every other `meta/` key send the batch to the log. A collMod or create with the option is a `meta/copt/` write: log. I found no batch where a catalog key reaches the lane.
- Fencing: `wait_agent` acknowledges only after slatedb's `await_durable` and a lease check; a skipped flush (another write's flush covered it) still waits for `await_durable`, so no shortcut acknowledges early.

## The cost arithmetic

- Re-ran `cost_agent_lane.py` against the unchanged reference model (`cost.py` md5 4807cbcd1742e75115bcabe696dde4af, checked): output identical to the owner's `cost_agent_lane.txt`. One PUT per 100 ms per database is 10 x 3,600 x 730 x 0.005 $ / 1,000 = 131.4 $ a month (ESTIMATED, DECLARED us-east-1 S3 price as in the model): correct.
- NOTE, changes the money: a transaction's commit flushes at once (no window), so a lane database that writes mostly in transactions pays one PUT per commit flush, bounded by one flush at a time, about 1 / PUT latency, not 1 / window. In the owner's own t5 at a 30 ms PUT: 1,138 commit flushes in the two 20 s transaction phases, about 28 PUTs a second (MEASURED from t5's counters), about 2.8 times the model's 10, so about 370 $ a month per database instead of 131 (ESTIMATED). At a 100 ms PUT the two match (about 9 a second). The model's PUT rate = min(writes, 1 / window) holds only for single writes. Whether LangGraph's checkpointer commits in transactions: UNKNOWN (not checked); the cost model should say which case a customer is.
- NOTE: the follower's 20 GETs a second (about 21 $ a month) are per followed database and run even when the database is idle (it probes the next number every 50 ms forever), so a spare following many quiet databases pays 21 $ each (ESTIMATED from the code).

## Other notes (do not block)

- The follower's memory (512 MB per process, kept objects never released except by size) and its starting point (only objects written after the spare started are followed) are fine for the prototype; R3's fix should also forget a database's objects when it is dropped.
- R2's window: the test uses a 4 s window only to land reliably; the hole exists at any window.
- The owner's t2 counts a fenced acknowledgement only when the write is missing at the end; I checked the stricter count (any acknowledgement from A after its wake) is also 0 in both runs.
- Brain: NOW.md says Q8d has no report and no review; with R4 and R5 open it should not be used in an AWS round as "the log" until fixed.

## What would change my mind

R3, R2, R5: a fix and the same tests passing (R2 and R5 both pass if a majority read never returns an unconfirmed write). R4: either the spare reads the log's records before it serves (the takeover replays the shared log for the database, as a restart does), or the coordinator decides the warm spare with the log is out of scope for this delivery; then R4 is a known gap for the warm spare owner, not a fix for the lane.
